1. **Создание виртуального окружения `my_env` и установка Django** (Лаб 1, стр. 2–3).
2. **Инициализация проекта `mysite`** командой `django-admin startproject mysite` (Лекция 2, слайды 2–4).
3. **Создание приложения `blog`** командой `python manage.py startapp blog` и регистрация `'blog.apps.BlogConfig'` в `mysite/settings.py` (Лекция 2, слайды 18–20; Лаб 1, стр. 8, 14).
4. **Проектирование модели `Post`** (`blog/models.py`, Лаб 1, стр. 9–17):
   - Поля: `title`, `slug`, `author` (внешний ключ `ForeignKey` на модель `User` с каскадным удалением `CASCADE`), `body`, `publish`, `created`, `updated`, `status`.
   - Перечисление статусов поста через `models.TextChoices` (`Draft` и `Published`).
   - Метаданные `ordering = ['-publish']` и индекс по убыванию даты публикации `models.Index(fields=['-publish'])`.
   - Пользовательский менеджер `PublishedManager` (`Post.published.all()`) для фильтрации только опубликованных постов (Лаб 1, стр. 30–31).
5. **Создание и применение миграций** (`makemigrations blog` и `migrate`, Лекция 3, слайды 15–21).
6. **Настройка панели управления `PostAdmin`** (`blog/admin.py`, Лаб 1, стр. 22–26):
   - `list_display`: колонки названия, слага, автора, даты и статуса.
   - `list_filter`: фильтры по статусу, датам и автору.
   - `search_fields`: поиск по заголовку и тексту.
   - `prepopulated_fields`: автоматическое заполнение слага из заголовка.
   - `raw_id_fields`: выбор автора через поисковый виджет.
   - `date_hierarchy`: навигация по датам.
7. **Представления и маршрутизация** (`blog/views.py` и `blog/urls.py`, Лаб 1, стр. 31–34):
   - `post_list`: выборка опубликованных постов через `Post.published.all()`.
   - `post_detail`: получение поста по `id` с помощью `get_object_or_404`.
   - Подключение маршрутов приложения в `mysite/urls.py` через `include` с `namespace='blog'`.
8. **Шаблоны и стили** (`blog/templates/blog/` и `blog/static/css/blog.css`, Лаб 1, стр. 35–38):
   - Базовый шаблон `base.html` с двухколоночным макетом (контент + сайдбар).
   - Наследование через `{% extends "blog/base.html" %}` и блоки `{% block %}`.
   - Фильтры `truncatewords` и `linebreaks` в выводе текста поста.

## 4. Шпаргалка для защиты перед преподавателем

### Вопрос 1: В чем суть архитектуры Django и чем MTV отличается от классического MVC?
> **Ответ:** 
> Django использует архитектурный шаблон **MTV (Model-Template-View)**:
> - **Model (Модель)** — описывает структуру данных и логику работы с базой данных.
> - **Template (Шаблон)** — слой представления (HTML), как данные видны пользователю.
> - **View (Представление)** — бизнес-логика: принимает HTTP-запрос, дергает данные из моделей и отдает их в шаблон.
> - Роль **Контроллера (Controller)** берет на себя сам Django (его диспетчер URL-адресов `urls.py`), который направляет запрос в нужную функцию-представление.

### Вопрос 2: Как устроен цикл «запрос–ответ» (Request / Response)?
> **Ответ:**
> 1. Пользователь вводит адрес (например, `/blog/1/`).
> 2. Веб-сервер передает запрос Django.
> 3. Django идет по `urls.py` (сначала в проекте, потом по `include` в приложении `blog`), находит совпадение маршрута.
> 4. Вызывается связанная функция во `views.py` (`post_detail`).
> 5. View обращается к базе данных через ORM (модель `Post`), забирает нужную запись.
> 6. Функция `render()` берет шаблон `detail.html`, подставляет данные (контекст) и возвращает готовый `HttpResponse` браузеру.

### Вопрос 3: Зачем нужны миграции и чем отличаются `makemigrations` и `migrate`?
> **Ответ:**
> Миграции нужны для отслеживания изменений в моделях и синхронизации их с таблицами в базе данных.
> - `python manage.py makemigrations` — анализирует изменения в файле `models.py` и создает файл инструкций (в папке `migrations/`), но в базу данных ничего не записывает.
> - `python manage.py migrate` — фактически выполняет сгенерированные инструкции в БД (создает или изменяет таблицы и колонки).

### Вопрос 4: Зачем мы создали кастомный менеджер `PublishedManager`?
> **Ответ:**
> По умолчанию у каждой модели есть менеджер `objects`, возвращающий все записи (`Post.objects.all()`). Мы создали свой менеджер `PublishedManager`, переопределив метод `get_queryset()`, чтобы отфильтровать посты со статусом `PUBLISHED`. Это позволяет удобно писать `Post.published.all()` и гарантировать, что черновики (`DRAFT`) случайно не попадут на страницу блога.

### Вопрос 5: Что делает `on_delete=models.CASCADE` во внешнем ключе `author`?
> **Ответ:**
> Каскадное удаление. Если из базы удалить пользователя-автора, Django и база данных автоматически удалят все связанные с ним посты в блоге, чтобы не оставалось «висячих» записей без автора.
